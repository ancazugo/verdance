    Development¶

    git clone https://github.com/sdgresearch/verdance.git && cd verdance
uv sync                                   # project environment in .venv, with the dev tools
uv run pytest                             # ~240 tests, about a minute and a half (Spark tests need Java)

    uv sync installs into .venv in the repository; to use an environment elsewhere, activate it and pass --active (uv sync --active, uv add --active <package>).

    End-to-end check. scripts/make_synthetic_city.py writes a small synthetic city (48 buildings, trees, parks, roads, a CHM and two census levels) and a config for it, so every module can run in a few minutes without downloads:

    python scripts/make_synthetic_city.py /tmp/verdance_synth
verdance run -c /tmp/verdance_synth/config.yaml -p T3 --buffer 50   # likewise T30, T300, Tree_count, Visibility, ...
verdance run -c /tmp/verdance_synth/config.yaml -p Merge --t3_buffers 50

    The other scripts in scripts/ prepare inputs for particular cities and evaluate tree segmentation and building heights against reference data.

    Documentation¶

    The site at https://sdgresearch.github.io/verdance/ is built with MkDocs Material from docs/. The config and API references are generated from the source by mkdocstrings, so editing a docstring updates the site.

    The docs toolchain is a separate dependency group, installed without the project itself — mkdocstrings reads the package statically, so building the site needs neither Spark, GDAL nor Java:

    uv sync --only-group docs
uv run --only-group docs mkdocs serve    # live preview at http://127.0.0.1:8000
uv run --only-group docs mkdocs build --strict   # what CI runs

    --strict turns broken links, missing anchors and unresolved API references into errors. Run it before pushing: the docs workflow builds on every pull request that touches docs/, mkdocs.yml or src/, and deploys to the gh-pages branch when master moves.

    Pages under docs/superpowers/ are internal design documents and are excluded from the published site.

    Releasing¶

    Releases are published to PyPI by GitHub Actions through trusted publishing, so no API token is stored anywhere. To cut one:

    1. Bump __version__ in src/verdance/__init__.py — [tool.hatch.version] reads it from there, so it is the only place the version is set.
    2. Move the [Unreleased] section of CHANGELOG.md under the new version number.
    3. Open a pull request, and once it is merged tag the merge commit and push the tag:
    git tag -a v<version> -m "v<version>" && git push upstream v<version>

    The tag triggers .github/workflows/release.yml, which builds the sdist and wheel and uploads them. To check a build locally first:

    rm -rf dist && uv build                   # dist/verdance-<version>.tar.gz and .whl
uvx twine check --strict dist/*
